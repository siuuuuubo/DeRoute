# 子任务拆解优先的复杂任务 DAG 与大小模型路由研究规划

> 文档版本：v1.0
> 整理日期：2026-09-03
> 当前阶段：课题启动与可行性验证
> 研究主线：先研究可执行子任务拆解，再研究节点级大小模型路由，最后扩展到负载感知联合决策

---

## 一、结论与总体定位

本课题值得继续，但不能将“子任务拆解 + 大小模型路由”本身作为唯一创新点。RouteGoT、RouteLLM、R2-Reasoner 等工作已经分别覆盖了图内路由、查询级大小模型路由以及分解后多模型分配。

当前最合适的研究推进方式是：

1. 先定义什么是可执行、可评测的子任务；
2. 建立复杂任务到子任务 DAG 的生成和评测管线；
3. 研究何时需要拆解、拆到什么粒度、何时停止；
4. 在拆解框架稳定后，加入节点级大小模型路由；
5. 最后研究关键路径和服务负载如何反向影响拆解粒度与路由决策。

阶段性课题名称建议为：

> **面向复杂任务的自适应子任务 DAG 生成与粒度控制**

完整课题名称可扩展为：

> **面向复杂任务的自适应子任务 DAG 生成、粒度控制与节点级大小模型路由**

长期框架可暂称 **AdaSplitRoute**。框架对每个尚未完成的节点执行三选一决策：

```text
DECOMPOSE          继续拆解当前节点
EXECUTE_SMALL      交给小模型执行
EXECUTE_LARGE      交给大模型执行
```

但三动作联合控制器不是当前阶段的第一项代码工作。当前首先要完成的是可信的任务图、拆解评测和节点执行管线。

## 二、核心研究问题

### 2.1 子任务拆解阶段

#### RQ1：复杂任务应如何表示为可执行子任务 DAG？

重点不是生成更多推理步骤，而是生成满足以下要求的节点：

- 目标单一且语义完整；
- 输入来源明确；
- 输出形式或类型明确；
- 前驱依赖明确；
- 具有可以检查的完成标准；
- 可以独立交给模型或工具执行；
- 不依赖未显式传递的隐藏信息；
- 节点间允许串行、并行、汇合和局部递归。

#### RQ2：如何评价拆解质量？

最终答案正确并不代表拆解正确。拆解至少要分别评价：

- 图是否合法；
- 节点是否覆盖原任务；
- 是否出现漏拆；
- 是否出现过拆；
- 节点语义是否匹配 Gold 子任务；
- 依赖边是否正确；
- 图是否暴露了真实并行机会；
- 节点能否被独立执行；
- 错误来自图生成、节点执行还是最终合成。

#### RQ3：什么时候应该停止拆解？

拆解不是越细越好。继续拆解可能产生：

- 更多模型调用；
- 上下文重复传输；
- 更长的串行关键路径；
- 更多合成和通信开销；
- 更严重的误差传播；
- 对全局语义的破坏。

建议将“停止拆解”研究为独立问题，而不是依赖提示词中一句模糊的“拆成合适粒度”。

### 2.2 节点路由阶段

#### RQ4：同一复杂任务内部是否存在稳定的节点能力异质性？

即一个根任务内部是否同时存在：

- 小模型稳定完成的节点；
- 大模型明显更可靠的节点；
- 两者都无法完成的节点；
- 结果随采样显著波动的节点。

如果这种异质性不明显，节点级大小模型路由就缺乏收益基础。

#### RQ5：如何预测指定小模型对节点的真实成功概率？

节点“难度”不使用 LLM 主观自评作为真值，而使用固定大小模型的重复执行结果构造标签。路由器预测：

```text
p_small_success(node)
```

而不是笼统预测 easy、medium 或 hard。

### 2.3 联合系统阶段

#### RQ6：图位置和系统负载是否会改变最优拆解与路由决策？

同一个节点在不同状态下可能有不同选择：

- 大模型空闲时，直接调用大模型可能更快；
- 大模型排队严重时，继续拆解并并行调用小模型可能更优；
- 关键路径上的边界节点应采用更保守的路由；
- 非关键并行节点可以更积极地使用小模型；
- 继续拆解如果增加关键路径长度，可能得不偿失。

## 三、创新边界与必须规避的重合

### 3.1 不能单独作为创新的内容

- 将简单问题交给小模型、复杂问题交给大模型；
- 固定拆解后对节点做 easy/hard 分类；
- 使用一个大模型生成计划，再让多个模型依次执行；
- 单纯将任务表示为 DAG；
- 只根据 Token 数量控制图展开；
- 关键路径调度本身；
- 多智能体角色设计；
- speculative decoding、early exit 或 prefill/decode 拆分。

### 3.2 建议坚持的差异

1. **拆解是运行时动作，而不是一次性前处理。**
2. **研究重点是拆解粒度，而不是在大型模型池中搜索。**
3. **路由标签来自中间节点的真实执行日志。**
4. **研究对象是可执行语义 DAG，不是任意思维片段。**
5. **最终将队列、关键路径和 SLO 纳入决策。**
6. **分别评测图生成、节点执行、路由和合成，保证错误可归因。**

### 3.3 与直接竞争工作的区别

| 工作                  | 已覆盖内容                                       | 本课题应保留的差异                                                    |
| --------------------- | ------------------------------------------------ | --------------------------------------------------------------------- |
| RouteGoT              | GoT 节点级路由、递归展开、成功率预测、Token 预算 | 研究可执行语义 DAG、拆解停止条件、队列和关键路径，而不仅是 Token 预算 |
| R2-Reasoner           | 顺序子任务分解、多模型分配、SFT + RL             | 先研究两级模型下的动态粒度和局部继续拆解，不以多模型池为核心          |
| RouteLLM              | 查询级强弱模型路由、偏好数据、成本阈值           | 将监督下沉到真实中间节点，并加入图结构特征                            |
| Select-Then-Decompose | 任务级拆解方法选择、验证和成本权衡               | 从任务级选择推进到运行时节点级停止/继续拆解                           |
| Murakkab              | 对已有工作流联合优化模型、硬件、成本与 SLO       | 研究开放问题如何生成、执行并动态细化任务图                            |
| Agentix               | 动态程序 DAG 和程序级调度                        | 负责语义拆解和模型能力决策，而不只是调度已有调用                      |

## 四、论文阅读规划

## 4.1 第一优先级：子任务拆解核心

### 1. Decomposed Prompting: A Modular Approach for Solving Complex Tasks

本地文件：[Decomposed Prompting](./子任务拆解/10_Decomposed_Prompting_A_Modular_Approach_for_Solving_Complex_Tasks.pdf)

这是当前最应该精读和复现的论文。重点理解：

- decomposer 与 sub-task handler 的分工；
- 子任务怎样引用前面步骤的输出；
- 子任务怎样由不同提示、模型或符号工具执行；
- 递归拆解怎样发生；
- 可执行子任务与普通 CoT 步骤的区别；
- 模块化拆解为什么更容易单独调试和替换。

可扩展方向：

```text
Decomposed Prompting：复杂任务 → 子任务序列 → handler
本课题：             复杂任务 → 可执行 DAG → 串并行执行
                                         → 动态停止或继续拆解
                                         → 后期加入节点模型路由
```

### 2. Least-to-Most Prompting

本地文件：[Least-to-Most](./子任务拆解/11_Least_to_Most_Prompting_Enables_Complex_Reasoning.pdf)

作用：建立最简单的“先分解、后按顺序求解”基线。后续需要证明 DAG 或动态拆解优于简单的子问题序列。

### 3. Select-Then-Decompose

论文：[Select-Then-Decompose（EMNLP 2025）](https://aclanthology.org/2025.emnlp-main.278/)

重点阅读：

- 一次性拆解与边执行边拆解；
- 链式、树式和图式拆解；
- 拆解模型与执行模型能力的组合；
- 哪些任务不适合拆解；
- 拆解方法的性能—成本 Pareto 前沿。

### 4. WorFBench

论文：[Benchmarking Agentic Workflow Generation（ICLR 2025）](https://proceedings.iclr.cc/paper_files/paper/2025/hash/adbe936993aa7cf41e45054d8b72f183-Abstract-Conference.html)

作用：学习 DAG 生成和图结构评测，包括节点、链、子图及未知任务泛化。限制是缺少完整的逐节点执行答案，因此它适合评测图生成，不适合单独训练节点路由器。

### 5. Tree of Thoughts

本地文件：[Tree of Thoughts](./子任务拆解/12_Tree_of_Thoughts_Deliberate_Problem_Solving_with_LLMs.pdf)

只借鉴“生成候选—评价—继续展开或停止”的搜索思想。必须明确：ToT 节点是竞争性的思维状态，本课题节点是共同完成任务的可执行单元。

### 6. ReAct

本地文件：[ReAct](./子任务拆解/13_ReAct_Synergizing_Reasoning_and_Acting_in_Language_Models.pdf)

借鉴执行反馈改变后续计划的机制。初期不实现完整智能体恢复和复杂工具环境。

## 4.2 第二优先级：数据集与拆解评测

### MuSiQue

论文：[MuSiQue（TACL 2022）](https://direct.mit.edu/tacl/article/doi/10.1162/tacl_a_00475/110996/MuSiQue-Multihop-Questions-via-Single-hop-Question)

优势：

- 每个多跳问题有底层单跳问题；
- 有逐步答案和支持段落；
- 有依赖 DAG；
- 适合隔离拆解、执行和路由误差。

限制：图较短，任务域主要是多跳问答，并行结构有限。

### FanOutQA

论文：[FanOutQA（ACL 2024）](https://aclanthology.org/2024.acl-short.2/)

优势：

- 人工子问题；
- 节点答案；
- `depends_on` 依赖；
- 大量 fan-out、并行分支和汇合；
- 与调研、聚合、比较等真实任务结构更接近。

它是拆解 DAG 评测的关键数据集。

### TaskCraft

论文与代码：[TaskCraft（ICLR 2026）](https://github.com/OPPO-PersonalAI/TaskCraft)

用于后期控制任务深度、宽度和工具链复杂度，研究动态拆解粒度。不要在第一轮引入。

### PARALLELPROMPT

论文：[PARALLELPROMPT（NeurIPS 2025）](https://proceedings.nips.cc/paper_files/paper/2025/hash/6bbefc73a187dd42e0dc065b4e7a0615-Abstract-Datasets_and_Benchmarks_Track.html)

适合后期串行/并行和系统时延实验。不适合训练节点正确性路由器，因为没有标准逐节点答案。

### MoNaCo

论文：[MoNaCo（TACL 2026）](https://aclanthology.org/2026.tacl-1.2/)

包含需要数十甚至数百个中间步骤的真实复杂问题。只在方案和阈值全部冻结后做最终严格留出测试。

## 4.3 第三优先级：大小模型路由

只有拆解器、DAG executor 和节点评测稳定后再精读和复现：

1. [RouteLLM](./子任务拆解/06_RouteLLM_Learning_to_Route_LLMs_with_Preference_Data.pdf)：学习二模型路由、阈值和成本—质量曲线；
2. [FrugalGPT](./模型路由/03_FrugalGPT_How_to_Use_LLMs_While_Reducing_Cost_and_Improving_Performance.pdf)：建立小模型优先、低置信升级的级联基线；
3. [CALM](./模型路由/07_CALM_Confident_Adaptive_Language_Modeling.pdf)：借鉴验证集校准和可控质量损失；
4. [BEST-Route（ICML 2025）](https://proceedings.mlr.press/v267/ding25d.html)：理解模型选择和 test-time compute 的联合决策；
5. [RouteGoT](./模型路由/01_RouteGot.pdf)：最直接竞争者，重点分析其 Success Predictor、Budget Predictor、PolicyNet 和全局预算调度；
6. [R2-Reasoner（WWW 2026）](https://doi.org/10.1145/3774904.3793038)：研究分解器和分配器的训练数据、SFT、RL 与奖励设计。

## 4.4 系统方向参考

- [Murakkab](./子任务拆解/01_Murakkab_Resource_Efficient_Agentic_Workflow_Orchestration_OSDI2026.pdf)：declarative workflow、profiling、SLO 和跨层优化；
- [Agentix](./子任务拆解/03_Agentix_Efficient_Serving_Engine_for_LLM_Agents_NSDI2026.pdf)：动态 DAG、程序级调度和数据局部性；
- [Teola](./子任务拆解/02_Teola_End_to_End_Optimization_of_LLM_Applications_ASPLOS2025.pdf)：细粒度数据流图、流水和跨模块并行；
- [Parrot](./子任务拆解/04_Parrot_Efficient_Serving_of_LLM_Applications_OSDI2024.pdf)：语义变量与调用依赖；
- [AI Metropolis](./子任务拆解/09_AI_Metropolis_Out_of_Order_Multi_Agent_Execution_MLSys2025.pdf)与[FlashAgents](./子任务拆解/08_FlashAgents_Accelerating_Multi_Agent_LLM_Systems_MLSys2026.pdf)：乱序、并行和流水执行；
- [BOute](./模型路由/02_BOute_Cost_Efficient_LLM_Routing_and_Deployment_MLSys2026.pdf)：路由与负载/部署的耦合。

## 4.5 暂不作为核心的论文

- LLM-Blender：多模型全部生成再融合，与降低调用成本的目标冲突；
- Splitwise：拆分 prefill/decode 计算阶段，不是语义任务拆解；
- Speculative Decoding：Token 级草拟与验证，不是节点路由；
- HELIOS：模型选择和层级早退，可借鉴 profiling，但不是语义拆解；
- Twill、RollArt：重点是硬件调度或训练系统；
- CoT、Self-Consistency、Zero-shot CoT：优化节点内部推理，不生成独立可调度 DAG；
- PAL：适合作为程序或工具节点基线，但不是通用拆解框架。

## 五、子任务和任务图的数据定义

### 5.1 TaskNode

第一版建议使用如下字段：

```python
class TaskNode:
    node_id: str
    goal: str
    inputs: list[str]
    expected_output_type: str
    dependencies: list[str]
    context: str
    completion_criteria: str
    depth: int
    parallelizable: bool
```

后期再增加：

```python
estimated_small_success: float
estimated_large_success: float
estimated_small_time: float
estimated_large_time: float
critical_path_slack: float
decomposition_depth: int
status: str
```

### 5.2 TaskGraph

```python
class TaskGraph:
    graph_id: str
    root_query: str
    nodes: dict[str, TaskNode]
    edges: list[tuple[str, str]]
    final_node_id: str
```

### 5.3 拆解器输出示例

```json
{
  "nodes": [
    {
      "id": "n1",
      "goal": "找出符合条件的实体列表",
      "inputs": ["root_query"],
      "output_type": "list[str]",
      "depends_on": [],
      "completion_criteria": "列表中的每个实体均满足给定条件",
      "parallelizable": false
    },
    {
      "id": "n2",
      "goal": "查询每个实体的目标属性",
      "inputs": ["n1.output"],
      "output_type": "dict[str, number]",
      "depends_on": ["n1"],
      "completion_criteria": "每个实体均有对应属性值",
      "parallelizable": true
    }
  ],
  "final_node": "n3"
}
```

### 5.4 DAG 校验要求

至少检查：

- 节点 ID 唯一；
- 边的两个端点存在；
- 图无环；
- 输入引用存在；
- 只有明确的最终 sink；
- 所有节点都能到达最终节点；
- 不存在与根任务无关的孤立节点；
- 输出类型与后继输入要求基本兼容；
- 并行节点之间不存在隐式数据依赖。

## 六、分阶段实现路线

## 阶段 0：研究协议与模型冻结

**预计时间：1 周**

完成内容：

- 固定小模型和大模型各一个版本；
- 第一阶段只做文本任务；
- 固定生成温度、最大 Token 和提示版本；
- 明确拆解器、执行器、合成器和 evaluator 的角色；
- 定义数据划分、缓存和日志协议；
- 明确 Gold 信息在不同实验中的可见范围。

阶段产物：

- `configs/first_round.yaml`；
- 一页实验协议；
- 数据泄漏检查表；
- 模型调用成本估算。

通过条件：任何实验都能明确说明是在测拆解、节点执行、路由、合成还是系统调度。

## 阶段 1：最小工程骨架

**预计时间：1–2 周**

优先实现：

1. `TaskNode`、`TaskGraph`；
2. DAG 校验与拓扑排序；
3. OpenAI-compatible 模型接口；
4. 响应缓存和断点续跑；
5. 调用次数、Token、费用和分段时延日志；
6. 串行 DAG executor；
7. Exact Match、F1、数值匹配；
8. 从缓存重建报告。

禁止提前实现：

- RL；
- 多智能体角色系统；
- LangGraph 可视化界面；
- vLLM 多 GPU 调度；
- 动态三动作控制器；
- 模型池搜索。

通过条件：使用手工构造的 3–5 个 DAG，在不调用模型的 mock 环境和实际小规模调用中都能稳定执行并重建报告。

## 阶段 2：Gold DAG 拆解与执行基准

**预计时间：2 周**

数据：MuSiQue。

完成内容：

- MuSiQue adapter；
- 将单跳问题和依赖转换为统一 TaskGraph；
- Gold DAG 串行执行；
- Gold 节点输出直接合成的上界；
- 大模型执行 Gold DAG；
- 错误分解为节点执行错误和合成错误。

比较：

```text
direct_large
gold_graph_all_large
gold_graph_gold_outputs
```

通过条件：可以对每个失败样本说明是节点执行、依赖传递还是合成出了问题。

## 阶段 3：零样本预测 DAG

**预计时间：2–3 周**

先使用冻结的大模型提示一次性输出结构化 JSON DAG，不训练拆解器。

比较：

```text
direct_large
least_to_most
decomposed_prompting
predicted_graph_all_large
gold_graph_all_large
gold_graph_gold_outputs
```

拆解指标：

- Valid-DAG Rate；
- 节点数偏差；
- Node Precision/Recall/F1；
- 语义节点对齐后的 Edge-F1；
- 任务覆盖率；
- 过拆率；
- 漏拆率；
- 最长路径偏差；
- 并行分支识别准确率。

通过条件：预测图合法率、节点覆盖和执行质量达到预注册门槛；门槛在 smoke 后、正式实验前冻结。

## 阶段 4：FanOutQA 并行和汇合结构

**预计时间：2–3 周**

完成内容：

- FanOutQA adapter；
- 解析人工 decomposition 和 `depends_on`；
- 支持 fan-out、并行分支与固定顺序汇合；
- 实现并行 DAG executor；
- 比较串行与并行执行的质量和时延；
- 人工复核固定样本的节点语义匹配。

通过条件：同一节点集合在串行和并行执行下保持语义一致，且并行实现不存在按完成顺序错误聚合的问题。

## 阶段 5：Gold DAG 节点能力画像

**预计时间：2–3 周**

此时才正式进入大小模型路由前置实验。

对每个节点：

1. 提供相同 Gold 支持上下文；
2. 提供相同 Gold 前驱输出；
3. 大小模型分别重复至少 3 次；
4. 使用规则指标为主、冻结 evaluator 为辅；
5. 生成如下标签：

```text
EITHER        大小模型都稳定成功
SMALL_ONLY    只有小模型稳定成功
LARGE_NEEDED  只有大模型稳定成功
UNSOLVED      两者都失败
UNSTABLE      重复执行不稳定
```

必须报告：

- 各标签比例；
- root-level mixed rate；
- 按节点类型、深度、长度和图位置分组的成功率；
- all-small、all-large、随机和 oracle route；
- profiling 额外成本；
- 根任务级 bootstrap 置信区间。

关键闸门：同一根任务内部必须存在足够的能力异质性。如果几乎所有节点都由同一模型占优，应先更换任务域或模型对，而不是直接训练路由器。

## 阶段 6：固定 DAG 上的节点路由

**预计时间：2–3 周**

预测目标：

```text
p_small_success(node)
```

特征分组：

- 文本：节点目标、输入、上下文、长度、embedding；
- 图结构：深度、入度、出度、后继数、是否处于关键路径；
- 执行信号：小模型置信、一致性、logprob、历史同类节点成功率。

模型按顺序比较：

1. 长度和节点类型规则；
2. Logistic Regression；
3. XGBoost 或 LightGBM；
4. embedding + MLP；
5. 小型 cross-encoder；
6. 最后才考虑 LLM router。

指标：

- `LARGE_NEEDED` Recall；
- AUROC、AUPRC、F1；
- ECE、Brier Score；
- 大模型调用比例；
- 相对 all-large 的质量下降；
- 成本—质量 Pareto 曲线。

通过条件：学习型路由稳定优于随机、长度规则和整题路由，并且质量下降处于预注册容忍范围。

## 阶段 7：动态拆解粒度

**预计时间：3–4 周**

动作空间扩展为：

```text
DECOMPOSE(node)
EXECUTE_SMALL(node)
EXECUTE_LARGE(node)
```

第一版使用离线反事实和规则/监督学习，不使用 RL。对同一节点记录：

- 直接小模型执行的质量、成本和时延；
- 直接大模型执行的质量、成本和时延；
- 继续拆解后的总体质量、成本和时延。

继续拆解净收益可定义为：

```text
U_decompose
= quality_gain
- lambda_cost * extra_cost
- lambda_time * extra_latency
- lambda_risk * propagation_risk
```

比较：

- 不拆；
- 固定粗粒度；
- 固定细粒度；
- 固定最大深度；
- 动态停止拆解；
- oracle 粒度。

后期加入 TaskCraft 和 WorFBench。

## 阶段 8：负载与关键路径联合决策

**预计时间：3–4 周**

先实现离散事件模拟器。每个模型维护：

```text
queue_length
estimated_wait
service_time_distribution
available_workers
token_throughput
```

每个节点维护：

```text
critical_path_slack
remaining_descendants
parallel_fanout
estimated_small_time
estimated_large_time
```

比较策略：

- 只按节点能力；
- 节点能力 + 图位置；
- 节点能力 + 队列；
- 节点能力 + 队列 + 关键路径；
- 动态拆解 + 联合路由。

报告：

- end-to-end p50/p95/p99；
- SLO 违约率；
- 大小模型利用率；
- 吞吐；
- 每任务成本；
- 拆解、等待、执行和合成分段时延。

## 九、评测和统计纪律

1. 训练、开发和测试按根任务分组，禁止按展开后的节点随机划分。
2. 同一个根任务的所有节点必须位于同一数据划分。
3. Gold decomposition、Gold 节点答案和依赖不得泄漏到端到端预测提示。
4. Oracle 实验必须单独配置并明确标注为上界。
5. 拆解器、执行器、合成器和 evaluator 的模型角色必须分离记录。
6. 规则指标优先，LLM evaluator 只用于无法规则判断的开放输出。
7. evaluator 模型、提示、温度和阈值在正式实验前冻结。
8. 大小模型对同一节点使用相同上下文和前驱输出。
9. 正式运行采用 paired repetitions，并记录失败、重试和限流。
10. 统计置信区间按根任务 bootstrap，不能把大量相关节点当作独立样本。
11. 原始响应必须缓存，报告能够从缓存和 manifest 一键重建。
12. profiling、拆解、执行、评测和合成成本分别报告。
13. 数据版本、模型版本、提示版本和 commit 必须进入 manifest。
14. 正式阈值在 smoke 后冻结，不根据正式结果事后修改。

## 十、主要风险与应对

| 风险                       | 表现                             | 应对                                             |
| -------------------------- | -------------------------------- | ------------------------------------------------ |
| 子任务定义模糊             | 节点像 CoT 片段，无法独立执行    | 强制输入、输出类型和完成标准；人工审计固定样本   |
| Gold DAG 与预测 DAG 难对齐 | 表述不同但语义相同               | 先做规则规范化，再做冻结语义匹配，人工核验校准集 |
| 过拆                       | 调用数、上下文和关键路径激增     | 单独统计过拆率和边际收益，建立停止拆解模型       |
| 漏拆                       | 节点内部仍需复杂多步推理         | 节点可执行性测试，记录节点内部失败类型           |
| 错误无法归因               | 最终答案错但不知道原因           | 固定 Gold 图、Gold 输出和预测图的分层实验        |
| 节点异质性不足             | 路由无法节省大模型调用           | 更换任务域或模型能力差距，不强行训练复杂路由器   |
| evaluator 漂移             | 指标随评测模型变化               | 规则指标优先，冻结评测器并人工复核固定样本       |
| API 成本过高               | 重复 profile 所有节点            | 小规模 smoke、缓存、先本地模型、先估算调用量     |
| 研究范围失控               | 同时做 Agent、RL、GPU 和多模型池 | 严格执行阶段闸门，上一阶段未验收不进入下一阶段   |
| 创新与 RouteGoT/R2 重合    | 只做拆解后模型分配               | 突出可执行 DAG、停止拆解、局部动态粒度和负载反馈 |

## 十三、预期论文叙事

如果最终实验成立，论文可以按以下逻辑展开：

1. 复杂任务内部的节点模型需求具有显著异质性；
2. 现有方法通常采用一次性拆解或固定粒度，造成过拆或漏拆；
3. 本文提出可执行语义 DAG 和局部动态拆解机制；
4. 控制器根据节点内容和图结构决定停止或继续拆解；
5. 在此基础上，根据真实节点成功率进行大小模型路由；
6. 系统负载和关键路径进一步改变最优粒度与路由阈值；
7. 在质量下降受控的条件下，系统减少大模型调用、成本和 p95 时延。

可能的贡献表述：

- 提出面向复杂任务的可执行子任务 DAG 表示与分层评测协议；
- 提出显式建模拆解收益与开销的动态粒度控制方法；
- 使用真实节点执行日志学习并校准大小模型成功概率；
- 提出结合节点能力、图位置和服务状态的联合决策方法；
- 在多跳问答、fan-out 任务和真实并行请求上验证质量—成本—时延收益。

## 十四、最终执行原则

1. 当前先把子任务拆解做正确、做可评测，再做模型路由。
2. 第一个可复现结果应是 Gold DAG 和预测 DAG 的误差归因，不是完整系统演示。
3. 第一个学习模型应是节点小模型成功率预测器，不是 RL 控制器。
4. 第一个系统实验应是离散事件负载模拟，不是多 GPU 集群。
5. 每一阶段都必须能独立产生可审查报告。
6. 如果阶段假设不成立，应调整问题或数据，而不是用更复杂模型掩盖。
7. 不把主观难度标签当作模型能力真值。
8. 不只报告最终准确率，必须报告图、节点、路由、成本和时延的分层指标。
9. 所有模型调用在正式批量运行前先估算次数、Token 和费用。
10. 研究价值来自清晰的可证伪证据链，而不是功能数量。
